# B1.1 — Regular Galaxy S10 hardware baseline

Status: **done — public source baseline established; device-specific handoff remains unverified**

## Target

Exynos Galaxy S10, codename `beyond1lte`, SM-G973F/DS and SM-G973N family.
Snapdragon variants are outside this target.

A teardown of an Exynos SM-G973F/DS identifies Exynos 9820, 8 GB LPDDR4X
and 128 GB UFS 2.1 on the examined unit:
https://chipwise.tech/our-portfolio/galaxys10/
A service-manual board diagram labels a 6 GB LPDDR4X configuration, so RAM
population is SKU/board-specific and must not be hardcoded from a model name:
https://www.manualslib.com/manual/1804558/Samsung-Sm-G973f.html?page=55
The regular S10 is 3040x1440; the S10e is 2280x1080:
https://www.ifixit.com/Teardown/Samsung%2BGalaxy%2BS10%2Band%2BS10e%2BTeardown/120331

## S10 board DTS findings

Reference: CruelKernel Samsung Exynos 9820, branch `cruel-HVJ5-v5.3`.

- Board DTS:
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/arch/arm64/boot/dts/samsung/exynos9820-beyond1lte_common.dtsi
  sets UFS CAL board type 16 (UNIV) and selects the S10 panel family.
- Touch DTS:
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/arch/arm64/boot/dts/samsung/exynos9820-beyond1lte_input_common.dtsi
  identifies BEYOND1/G973, firmware `tsp_sec/y771_beyond1_phole.bin`,
  TCLM level 2, AFE base 0x0206 and FOD support.
- Shared key DTS:
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/arch/arm64/boot/dts/samsung/exynos9820-beyondlte_input_common.dtsi
  lists KEY_WINK/Bixby at gpa0-6 (Linux code 703), volume down at gpa0-4
  (114), volume up at gpa0-3 (115), power at gpa2-4 (116), all with
  10 ms debounce. KEY_WINK and power are wake-capable. GPIO flag cell 0xF
  must be decoded from the binding/pinctrl before setting polarity.
- Display: `&dsim_0` selects `s6e3ha9_beyond1`; panel reset/power is
  gpa3-4. The lookup includes 1440x3040 L-cut/U-type and a 1440x2960
  temporary panel. Exact revision is unknown.
- USB: `&usbdrd_dwc3` selects OTG and SuperSpeed Plus with Samsung quirks;
  `&usbdrd_phy0` uses gpg0-4 as the PHY-port selector. The S10 and S10e
  common DTS files have the same HS host tuning and SS tuning tables in this
  kernel branch.
- USB-C/PD: S10 EVT1 overlay
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/arch/arm64/boot/dts/samsung/exynos9820-evt1-beyond1lte_if-pmic-max77705.dtsi
  places MAX77705 at HSI2C45 address 0x66, IRQ gpa1-6, with
  `support_pd_role_swap`. This matches the existing PMIC driver's controller
  family and bus, but the overlay is revision-specific; confirm DTBO selection.
  Do not use the generic S2MM005 reference-board fragment as phone evidence.
- Shared Exynos 9820 DTS:
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/arch/arm64/boot/dts/exynos/exynos9820.dts
  declares UFS HCI 0x13D60000, vendor HCI 0x13D61100, UniPro 0x13D50000,
  UFSP 0x13D70000, PHY/PMA 0x13D64000, I/O coherency 0x13C10700 and
  CPORT 0x13D68000. It declares clocks GATE_UFS_EMBD/UFS_EMBD,
  dma-coherent, hw-rev 6, event version 1, two lanes and Gear 3. S10 board
  override sets CAL board type 16.
- Do not call the handset's storage UFS 3.0: the examined SM-G973F/DS teardown
  identifies UFS 2.1 NAND. The SoC CAL's Gear-3-capable tables are not a
  marketing/specification claim about the NAND.
- UFS CAL source has EVT0/EVT1 tables, G3/G4 post-init tables and separate
  pre/post-link, hibern8 and PMC flows:
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/drivers/scsi/ufs/ufs-cal-9820.c
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/drivers/scsi/ufs/ufs-cal-9820.h
  The CAL header defines UNIV as bit 4 (16). Trace the kernel parser for
  `brd-for-cal` before porting that value; `ufs-exynos.c` also has a
  `p->board = 0` default that needs tracing:
  https://github.com/CruelKernel/samsung-exynos9820/blob/cruel-HVJ5-v5.3/drivers/scsi/ufs/ufs-exynos.c
- The vendor DTS window extents differ from some larger/superset sizes in
  the existing `Exynos9820.h`: HCI +0x200, VS +0x200, UniPro +0x8000,
  UFSP +0x100, PMA +0x800, I/O coherency +0x4 and CPORT +0x804.
  Existing S10e task T03 tracks this discrepancy; it is not closed by the
  S10 board override.

## Do not carry over S10e-only values

The current `Beyond0LtePkg` and `Exynos9820.h` include S10e live-read
assumptions: RAM bank extents and reserved carveouts; framebuffer base
0xCA000000, 1080x2280 geometry and 10 MiB reservation; UFS DMA window
0xA7400000..0xBAB00000; S6E3FA7 panel and y761/AFE 0x0205 touch settings.

For the S10, 1440x3040 at 4 bytes/pixel is 17,510,400 bytes for one tightly
packed frame, already larger than the S10e 10 MiB reservation. Actual stride,
format, buffer count and framebuffer base are unknown. Do not simply change
width/height while retaining the old base or reservation.

The vendor SoC DTS has generic 2 GiB memory nodes, while the existing S10e
live map differs; the regular S10 teardown also shows SKU-level RAM
differences. A correct S10 memory map must come from its actual DTB/live
handoff, not a guessed 8 GiB linear range.

## Reuse classification

| Area | Conclusion |
|---|---|
| UFS/USB controller MMIO | Shared Exynos 9820 source candidates; resolve extent/clock/reset issues |
| UFS CAL board | S10 DTS says 16 (UNIV); trace parser before use |
| UFS DMA aperture / RAM | S10e-only live values; do not reuse |
| USB PHY tuning / OTG | Same S10/S10e values in examined kernel branch |
| USB-C PMIC | MAX77705 on HSI2C45; confirm exact hardware-revision overlay |
| Display controller | Shared SoC blocks; S10 panel and framebuffer are different |
| Panel | S6E3HA9 1440x3040 family; exact variant unknown |
| Buttons | GPIOs source-defined; electrical polarity/pinmux still needs decoding |
| Touch | S10-specific y771 / AFE 0x0206 / FOD |
| RAM / boot handoff | Not established for regular S10 |

## Next steps

1. Add a dedicated `Beyond1LtePkg` in this same repository, leaving the
   S10e package as an untouched reference.
2. Separate shared Exynos 9820 MMIO from board-specific memory, framebuffer,
   PMIC, panel and input configuration.
3. Audit UFS DMA/FMP and USB-C power/role paths before reusing the existing
   driver code.
4. Build a safe GOP path only after framebuffer base/extent/format are known.
5. Implement GPIO input only after polarity, pinmux and interrupt semantics
   are resolved.
6. No flash or destructive tests until a regular S10 and recovery route exist.
