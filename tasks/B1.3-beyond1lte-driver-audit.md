# B1.3 — Audit inherited S10e driver side effects and S10 handoff blockers

Status: **doing**

## Goal

Before implementing the S10 platform DSC, identify which existing
`Beyond0LtePkg` modules can be reused safely and which perform S10e-specific
memory accesses, secure-monitor calls, PMIC writes or framebuffer writes.

## Findings recorded so far

### Memory and boot handoff

- The generic Exynos 9820 DTS declares memory nodes at
  0x80000000+2 GiB, 0x880000000+2 GiB and 0x900000000+2 GiB. This is a
  generic 6 GiB layout, not proof of the regular S10's actual RAM map.
- The same generic DTS contains reserved-memory regions including
  `sec_rdx_bootdev`, `debug_snapshot`, `abox-rmem` and `seclog_mem`.
  Their placement/size and the final live map may be changed by Samsung's
  bootloader.
- The existing `Exynos9820.h` contains S10e live values: bank0
  0x80000000+0x3AB00000, bank1 0xC0000000+0x20000000, bank2
  0xE1900000+0x1E700000, and high banks at 0x880000000 and 0x900000000,
  each 2 GiB. Those values are not a regular-S10 measurement.
- A teardown identifies an 8 GiB S10 unit, while the SM-G973F service-manual
  board diagram labels 6 GiB. Treat capacity as SKU-dependent and do not
  invent high-bank extents.
- `ArmPlatformLib.c` has S10e-specific early splash writes to
  `EXYNOS_FB_BASE`, fixed scratch writes at 0x8FE0F000, and watchdog/PMU
  writes. These must not be copied into the S10 package without replacing
  each address/side effect with S10-specific evidence.
- No DTB pointer or post-sboot memory-map handoff has yet been established
  from the existing EDK2 entry path. Trace the boot image/SEC entry before
  designing a runtime FDT parser.

### UFS

- Existing S10e UFS DMA window in `drivers/Exynos9820Ufs/Exynos9820Ufs.h`
  is 0xA7400000..0xBAB00000 and was selected from S10e live bank0 and
  reservation boundaries. Do not copy it.
- Existing UFS HC driver calls `Beyond0LteUfspConfig()` during controller
  initialisation (call site around line 1506). That routine performs active
  secure-monitor calls for FMP security, SMU init/resume/dump, disk-key
  store/set and UFS logging. It also submits an embedded static disk-key
  buffer. These calls are NOT all hidden by `BEYOND0LTE_UFS_DIAG=0`;
  that flag only gates diagnostics. Do not reuse this routine for S10.
- The UFS host driver also changes the I/O-coherency register and uses
  hand-coded HCE/UniPro/PHY/SMU recovery sequences. Each write must be
  compared against the S10 kernel's exact revision and the inherited sboot
  secure context. The new S10 path must start read-only and must not set a
  new FMP disk key speculatively.
- Shared DTS UFS addresses are useful source candidates, but the HCI/VS/UFSP/
  CPORT extent disagreement with the existing header remains open. The
  `brd-for-cal=16` DT value must be traced through the kernel parser before
  being used in a UEFI CAL implementation.

### USB / Type-C

- Existing S10e `Beyond0LteUsbHostDxe` defaults host bring-up and Windows
  exposure on. It calls the MAX77705 path and can enable VBUS boost.
- `Pmic.c` configures HSI2C45, probes MAX77705 clients, changes CCIC
  configuration, switches the USB data path and writes charger registers
  to enable OTG/VBUS. These are active power/role changes, not passive reads.
- S10's EVT1 overlay confirms MAX77705 at HSI2C45 address 0x66 and role-swap
  support, but it does not validate the existing host/VBUS policy for every
  S10 hardware revision.
- New S10 target must keep host mode, CCIC reconfiguration and VBUS boost
  disabled until the exact DTBO revision and safe role/power sequence are
  established. Device mode and host mode need separate, explicit policies.

### Display / touch / input

- Existing framebuffer base 0xCA000000, 1080x2280 geometry and 10 MiB
  reservation are S10e live assumptions. A 1440x3040 32-bit frame alone
  needs about 16.7 MiB; stride, format, buffers and base remain unknown.
- Existing early splash and GOP code must not run against the S10e base.
  First display milestone should preserve/describe the bootloader's active
  scanout only after its S10 handoff parameters are known.
- Existing touch-power module writes S2MPS19 rails through ACPM. The S10
  touch firmware/AFE differs; verify its rail node and power sequence before
  enabling writes.
- No UEFI GPIO-key driver is present in the current Beyond0Lte package.
  The S10 key GPIO names are known from DTS, but the GPIO flag/polarity and
  input interrupt semantics still need a binding/pinctrl trace.

## Acceptance criteria

- [ ] Trace the Samsung boot image and SEC entry path; establish whether an
      FDT or equivalent memory-map handoff is available to UEFI.
- [ ] Extract/classify all S10e-only fixed RAM addresses used before DXE.
- [ ] Trace UFS HCE/SMU/FMP side effects and identify a safe S10 read-only
      bring-up sequence without an embedded disk key.
- [ ] Trace MAX77705 CCIC/charger writes and define a disabled-by-default
      S10 host/role policy.
- [ ] Define the S10 framebuffer discovery strategy and touch/button power
      boundaries.
- [ ] Record which modules can be reused unchanged, require board adaptation,
      or must be rewritten.
